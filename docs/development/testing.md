# How the test suite is set up

Tests carry no comments. The reasons behind the less obvious parts of the suite live here, grouped by file.

## tests/shared

- `isolate-home.ts` is a Vitest setup file that gives every test file its own temp home. Onboarding, `join`, update and the stage-agent writer all write under the user's home (`~/.paqad-ai/current`, `~/.claude/agents`, `~/.codex/agents`). With the real home in place, a local run once repointed the developer's global paqad at the checkout's `runtime/`, so every project on the machine ran unreleased hooks. It sets both `HOME` and `USERPROFILE`, because `os.homedir()` reads `USERPROFILE` on Windows. It also expands Windows 8.3 short names (GitHub runners report `C:\Users\RUNNER~1\...`), since a `~` in the home leaks into every absolute path built from it.
- `duration-sequencer.ts` splits `--shard` runs by how long each file takes. Vitest's own split hashes paths into equal file counts, so one slow file can pile onto a full shard. The sequencer reads per-OS timings from `tests/shard-timings.json` and hands files out longest first to the lightest shard, ties broken by path so every run splits the same way. A file with no timing gets the median. A stale timings file only makes shards less even; it can never skip or repeat a test. A missing or broken file falls back to Vitest's split, and an unsharded run never calls it.
- `pack-manifest.ts` parses `npm pack --json` in both shapes: npm 11 and older print a top-level array, npm 12 prints an object keyed by package name. The release job installs the latest npm, so this must stay shape-agnostic.
- `legacy-stage-row.ts` writes a stage-evidence row in the old schema version 1 shape. Writers only produce the current shape, so a test proving a reader still accepts an old bundle has to put the old row on disk itself.
- `spec-pipeline-off.ts` pins the spec pipeline, the experts and strict adoption off in a temp project's team layer. These switches default on, so a test that proves the switched-off path must set them off explicitly. A later `.paqad/.config` in the same test still wins key by key.
- `ticket-ref.ts` builds an issue-like token (`#` plus a number) for test inputs that must contain one, so test sources never carry a literal issue number.

## tests/e2e

- `stage-enforcement-contract.e2e.test.ts` drives the real `runtime/hooks/*.mjs` scripts over a temp onboarded repo and checks their block and allow decisions on both the npm route (no `CLAUDE_PLUGIN_ROOT`) and the plugin route (`CLAUDE_PLUGIN_ROOT` set). Both routes run the same scripts, so the test proves enforcement is identical under both. Block means exit code 2 with a message on stderr; allow means exit 0. Its cases, names and assertions must stay unchanged. Each hook runs with a clean env (only `PATH` kept) so the real session's ids never leak into the child, and an empty `CLAUDE_PLUGIN_ROOT` must read as unset. The rules-loaded block has no case here: it only arms with compiled, script-enforced rules, which a bare temp repo cannot produce reliably, so it is covered by the rules-loaded enforcement suite. The malformed-payload case runs against a temp repo because a payload with no session id falls back to the legacy sentinel, and an in-process call would read the developer's own repo.
- `helpers/ensure-built.ts` builds `dist` once under the shared e2e lock when it is missing or older than `src`, so parallel workers never race on `pnpm run build`.
- `dist-runtime-root.e2e.test.ts` runs against the built bundles and the real `verify-backstop.mjs`. The Stop hook imports the depth-one `dist/index.js` while the CLI runs the depth-two `dist/cli/index.js`; a fixed relative path once resolved one folder too high from the first, and only built bundles show that.
- `hud-snapshot.e2e.test.ts` imports through a file URL because `import()` rejects a bare Windows path. A Windows read that lands mid-rename (EPERM or EBUSY) counts as a missed read, not a broken file.
- `onboarding-interactive.e2e.test.ts` drives the built CLI through a real pseudoterminal with the system `expect(1)` binary, walks the full interactive prompt chain and picks "No, skip" on RAG. That path once hung on a stuck readline handle, and every other e2e passes full overrides that skip inquirer. It skips itself where `expect` is missing (Windows, small containers).
- `join.e2e.test.ts` points both `HOME` and the framework home at the temp dir, because `join` runs the global install.
- `package-readiness.e2e.test.ts` treats a `dist` built from an older version as a missing build, and gives `npm pack --dry-run` more time on Windows and on a cold, fully parallel container.
- `archetype-detection.e2e.test.ts` and `rag.e2e.test.ts` raise their timeouts for the slow Windows runner; those runs are slow, not hung.
- `reranking.test.ts` injects the resolved RAG profile through the read path, because the advanced RAG internals resolve from code defaults rather than project config.

## tests/unit

- The onboarding adapter matrix is split over `matrix.g1.test.ts` to `matrix.g5.test.ts`, sharing `matrix-harness.ts`. As one file it took 440s on Windows and set a floor no shard count could beat, because Vitest shards by file. `matrix-partition.test.ts` proves the five groups still cover every fixture once. The harness treats an absolute path in a file paqad itself git-ignores (a sibling `.gitignore` lists it) as intended, not a portability leak.
- Heavy onboarding tests (`create-project`, `onboard-installed-stack`, `readiness`) onboard once in `beforeAll` and copy the result per test, so the Windows worker is not starved by back-to-back onboarding runs.
- `runtime/temp-project.ts` removes temp projects with a shared retry budget (50 tries, 100 ms apart), because a detached context-refresh child can keep writing after a gate returns and make an immediate delete fail with ENOTEMPTY. Tests that do not need the refresh pass `NO_CONTEXT_REFRESH_ENV` so it never starts.
- `skills/_helpers/run-script.ts` can log every non-zero script result to the file named by `PAQAD_DEBUG_RUNSCRIPT`, so CI flakes can be read from their real stderr. An old "lint script rejects a valid block" flake came from `set -o pipefail` with `printf | grep -q`, where an early-exiting grep killed printf with SIGPIPE; the scripts use here-strings now and a portability guard keeps the racy form out.
- Wall-clock bounds (for example the 100k-vector scan in `rag/crs-collection.test.ts`) are generous on purpose: shared CI runners vary several-fold, and a quadratic regression would still take seconds.
- Date fixtures that feed a staleness window (`patterns/patterns.test.ts`) are relative to now, because a fixed date silently crosses the threshold as time passes.
- `guardrails/changeset.test.ts` runs `changeset status` against the merge base with `origin/main` and expects the pending changesets to release `paqad-ai`, with any bump. It is a local check: a CI clone has no `origin/main`, so it skips there and says why, and it also skips when nothing has changed since `origin/main`.
- Permission tests skip on Windows and as root: `chmod 0o000` does not block reads on Windows, and root ignores file permissions.
- Under ESM `node:fs` cannot be spied on, so a disk-full test fails the orchestrator's own write entry point instead, which is exactly what the guard wraps.
