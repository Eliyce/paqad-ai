---
'paqad-ai': patch
---

paqad no longer writes other tools' MCP config files (#622). Older versions wrote paqad's own MCP suggestions to `.cursor/mcp.json`, `.vscode/mcp.json`, `.junie/mcp/mcp.json`, `.codex/mcp.json`, `.windsurf/mcp.json`, `.continue/mcp.json`, `.gemini/mcp.json`, `.antigravity/mcp.json` and `.claude/settings.mcp.json` on every onboard and update. Those files belong to the tools that read them, so any MCP server you had set up in one of them was replaced and lost. We are sorry about that.

Now the suggestions live in paqad's own `.paqad/mcp-recommendations.json`, as a plain list of server names, what each one provides and why it fits your stack. paqad never configures a server for you. On the next onboard or update, paqad removes only the files it wrote itself: a file is deleted only when it carries paqad's `resolved_artifacts` marker, holds nothing at the top level besides that marker and `mcpServers`, and none of its servers has a `command`, `url`, `type`, `serverUrl`, `args`, `env`, `headers` or `transport`. Every other file is left exactly as it is. When a file carries paqad's marker but is kept anyway, `.paqad/logs/mcp-cleanup.log` says why; your own files without the marker are not logged. `paqad-ai join` only removes git-ignored copies, so it still changes no tracked file.

If you lost an MCP server to an older version and the file is tracked in git, you can find your old setup with `git log -p .cursor/mcp.json` (use the path of the file you lost) and copy the server back.

`paqad-ai doctor` now reports MCP as `MCP servers (recommended)` with an `info` status. It lists the servers suggested for your stack and the ones already in your root `.mcp.json`, and it never passes or warns. An `info` check does not change the overall doctor result. The dashboard says "MCP server(s) recommended" instead of "Configured".

`paqad-ai new project` now ends with its own panel (#612). It says the workspace was created, that the application stack is still undecided, and gives one next step: choose your application stack, by running discovery or `paqad-ai onboard` once the stack exists. It no longer shows the onboarding steps such as "create documentation", which only make sense once a stack exists. `paqad-ai onboard` shows the same panel as before.

Site map evidence on Laravel now points at real files (#500). A route found by `php artisan route:list` cites the route file line that declares it and the controller method that handles it, a console command cites the class that declares it, and a scheduled task cites the line that schedules it. The artisan command now lives only in the evidence note, so a map that cites `routes/web.php` no longer reads as missing a route that artisan found. A route that a package registers cites its file under `vendor/` when your dependencies are installed; otherwise it lands in the blocked check. A route or schedule that cannot be traced to a file, such as a closure, is shown as a blocked check that lists it, instead of being added with no file. A command scheduled by its class, like `Schedule::command(SendReports::class)`, is found through that class. Artisan built-ins with no source in your project are skipped. Artisan also runs the way your project runs it, read from the migrate command in `.paqad/project-profile.yaml`: Sail (a bare `sail` means `vendor/bin/sail`), docker compose `exec` or `run` (run with no terminal), or host PHP. Leading settings like `APP_ENV=testing` are dropped. If that command still holds a placeholder like `<php-service>`, or chains commands with `&&`, `||`, `;` or `|` before artisan, the map tells you what to fix. Because the evidence changed, an existing Laravel map reads as drifted once after this update; run the map again to refresh it.
